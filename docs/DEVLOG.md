# 开发记录

> LyricLume（译光）从想法到 v1.0.0 的完整过程、踩过的坑、以及为什么这么做。

---

## 一、起点：需求

Spotify 自带歌词对日语歌几乎不做中文翻译。用户日常用的是 QQ 音乐，觉得它的翻译质量好，想要：

- 歌词 + 翻译在**同一个界面**（不是单独开一个翻译窗口）
- 一个按钮开关翻译
- **逐字染色**，并且译文要跟着原文一起变色
- 染色是**连续扫过**，不是整句突变
- 可以选配色

结论先说：**Spotify 没有插件体系，也没有公开歌词 API。** 唯一可行路径是 [Spicetify](https://github.com/spicetify/cli) —— 它给桌面客户端打补丁，允许加载自定义 JS。所以产品边界很早就定了：**Windows 桌面版，手机和网页端不可能。**

## 二、数据源：把 QQ 音乐拆开

### 1. 歌词有两种

| 接口 | 返回 | 时间精度 |
|---|---|---|
| `fcg_query_lyric_new.fcg` | base64 LRC | 整句 |
| `musicu.fcg` + `GetPlayLyricInfo` + `qrc:1` | 加密 QRC | **逐字** |

QRC 解出来长这样：

```
[238606,6160]今(238606,384)で(238990,328)も(239318,328)あ(239646,336)...
```

`[行起始, 行时长]` 后面跟 `字(起始, 时长)`。这就是逐字染色的数据基础。

### 2. 翻译只有「行级」

`trans` 字段是普通 LRC，只有整句时间戳。**这是整个项目最核心的限制**——原文有逐字时间，译文没有。

### 3. 解密链路

```
hex 字符串
  → 3DES（QQ 魔改版，不是标准 DES）
  → 得到 zlib 流
  → 解压
  → XML，里面 LyricContent 属性就是 QRC 文本
```

魔改 3DES 的实现在 [LDDC](https://github.com/chenmozhijin/LDDC) 里（Python），我把它移植成了 JS。

**验证方式**：同一段密文分别用 Python 和 JS 解，比对 `sha256`——**逐字节一致**才算过。这一步不做，后面所有染色都是错的。

### 4. zlib 尾巴的坑

密文按 8 字节分块，明文末尾带填充垃圾。浏览器 `DecompressionStream` 遇到多余尾巴直接抛 `ERR_TRAILING_JUNK_AFTER_STREAM_END`。

解法：
- Node 端：`inflateSync(buf, { finishFlush: Z_SYNC_FLUSH })`
- 浏览器端：从尾部**逐字节**往回砍，重试到成功（砍 8 字节的倍数不对，必须逐字节）

### 5. 匹配

Spotify 只给标题/歌手/时长，QQ 音乐搜索出来的候选要打分：

```
分数 = 标题相似度 × 60 + 歌手相似度 × 40 + 时长惩罚
时长差 ≤2s  +60
        ≤4s  +30
        ≤8s  +10
        >8s  −40
```

实测 5 首日文歌：**5/5 匹配正确，时长差 0~1 秒，翻译覆盖率 95~100%**。

## 三、渲染：逐字染色怎么做的

### 核心思路

1. 每个词/字渲染成独立 `<span>`，挂载后量出 `offsetLeft + width`
2. 播放时把「时间」映射成「横向像素位置」：唱到第 3 个词的 40%，边缘就停在第 3 个词左边 40%
3. 上层文字用渐变填色，裁一条 `clip-path: inset(0 calc(100% - Xpx) 0 0)`

得到的是**一条连续移动的边缘**，而不是整块跳变。

### 译文怎么跟上

按原文每个词的**时长占比**，把译文字符分配过去：

```
言えずの(2.0s) 「I(1.6s) love(1.8s) you」(2.4s)
说不出口的      「I      love      you」
```

同一时刻，原文的进度映射到译文分配的字符位置上，两条线的边缘同步推进。

这解释了为什么 `I love you → 我爱你` 能对上：三个词时长接近，正好三字对三词。

## 四、踩过的坑（按痛感排序）

### 1. `getShuffle()` 把后面所有事件绑定全弄死了 ⚠️ 最坑

症状：音量按钮、进度条、滚轮、点歌词跳转**全部失灵**，但歌词能正常显示。

原因：初始化时调了 `Spicetify.Player.getShuffle()`，它在播放器状态没就绪时抛 `Cannot read properties of undefined (reading '_state')`。异常发生在**事件绑定之前**，导致后续 `addEventListener` 一行都没执行。

教训：**任何第三方 API 调用都要 try/catch**，尤其是在初始化阶段。这个 bug 找了两个小时。

### 2. flex 居中导致滚动偏移算了两遍

症状：当前句不居中，总是偏。

原因：`.qql-body` 是 `display:flex; align-items:center`，5000px 高的歌词轨道先被垂直居中了一次，我又叠加了一个 `translateY`。

解法：改成 `display:block`，滚动完全由 translate 控制。

### 3. Spotify 没有 Node 权限，还挡 CORS

调研结论：

| 方案 | 结果 |
|---|---|
| `require('https')` | ❌ `require is not defined` |
| 浏览器 `fetch` 直连 QQ | ❌ CORS 拦截 |
| **本地代理** | ✅ |

代理只监听 `127.0.0.1:8787`，不对外暴露。

### 4. `element.click()` 点不动 Spotify 的列表

症状：用 JS 点歌曲行，播放不切换。

原因：Spotify 用的是 **pointer 事件**，合成 `click` 不触发它们的 handler。

解法：通过调试端口发**真实鼠标事件**（`Input.dispatchMouseEvent` 的 mousePressed/mouseReleased）。

### 5. React 重渲染把入口按钮挤到错误位置

症状：从「歌词预览」切到「歌词」时，`译光` 按钮跑到标题旁边去了。

原因：切换时 Spotify 重建了那一栏的 DOM，我的按钮被插进了错误的父节点，而且之后没人再管它。

解法：每次 DOM 变化/轮询都**校验父节点**，不对就移回去。

### 6. zlib 解压报错

见上文「zlib 尾巴的坑」。

### 7. PowerShell 5.1 读无 BOM 的 UTF-8 会乱码

症状：`install.ps1` 里的中文全变成乱码，脚本语法错误跑不起来。

解法：`.ps1` 必须存成 **UTF-8 with BOM**。

### 8. winget 装 GitHub CLI 卡死

症状：`winget install GitHub.cli` 卡 10 分钟不动。

原因：MSI 在等 UAC 提升弹窗，而这个环境弹不出来。

解法：改用免安装 zip（`gh_x.x.x_windows_amd64.zip`），解压即用。

### 9. GitHub 拒绝 push：邮箱隐私保护

症状：`GH007: Your push would publish a private email address`。

解法：提交作者改成 GitHub 的 noreply 邮箱：

```
<用户ID>+<用户名>@users.noreply.github.com
```

## 五、几个设计决定

| 决定 | 原因 |
|---|---|
| **全屏浮层**而不是接管原生歌词页 | 完全不依赖 Spotify 的页面结构，改版砸不到；代价是入口要注入 |
| 入口按钮**注入原生歌词栏** | 用户已经在看歌词了，这时候看到按钮最自然 |
| 圆形 `clip-path` 展开 | 从按钮位置扩散，视觉上「长出来」；比缩放不变形 |
| 歌词全是白色 | 封面颜色不可预测，灰色在红/黄封面上完全看不清 |
| 不加文字阴影 | 加过，但染色部分会蒙一层灰，对比后去掉 |
| 翻译开关按钮叫「译」 | 一个字，最小视觉占用 |

## 六、性能

- 首次抓取：130~250ms/首
- 缓存后：0（localStorage）
- 逐字染色：60fps，只更新一个 CSS 变量
- 部分歌词测量在每帧按需重测（字号过渡会改宽度）
